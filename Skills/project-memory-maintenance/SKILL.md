# 项目记忆维护

通过“短活跃索引 + 可追溯历史记录”控制召回上下文。维护不会删除正式记录：旧事实保留在原文件中，标记为 `superseded` 或 `deprecated` 后移出活跃索引。

## 启用检查

复用 `$project-memory` 的项目配置：`启用` 必须为 `是`，`项目名称` 必须存在，Vault 根目录优先使用 `CODEX_MEMORY_VAULT`，其次使用 `Vault根目录`。缺失任一值时停止，不猜测路径。

## 维护流程

脚本路径分别从本 `SKILL.md` 和已安装的 `$project-memory` 目录解析，不要假设当前项目包含 `Skills/` 源码目录。

1. 先运行 `<project-memory Skill目录>/scripts/memory_store.py maintenance-audit`。它只读取元数据并输出规模、陈旧记录、摘要新鲜度和候选分组，不把全部正文装入上下文，也不修改知识库。
2. 如果活跃记录不超过 60 条、活跃索引未触及 6,000 字符硬上限、`当前状态.md` 正文不超过 80 行，并且没有明显重复主题，只运行验证后结束。阈值是维护信号，不是强制丢弃事实的额度。
3. 需要语义合并时，阅读 [合并规则](references/consolidation.md)，再运行本 Skill 的 `scripts/memory_maintenance.py audit` 发现完全重复、近义和冲突候选。每批默认最多检查 12 条同类型、同模块候选；正文合计接近 24,000 字符时提前分批。
4. 用当前代码、测试、提交或用户确认复核候选。无法确定仍然有效的内容不要合并，可标记为待复核但不得编造结论。
5. 将多条同主题事实合并进一个稳定 ID 的原子记录，正文只保留当前结论、适用范围、关键例外和可核验来源。通过 `upsert --supersedes <旧ID>` 写入；存储脚本会把旧记录标记为 `superseded` 并移入历史索引。
6. 用 `write-summary` 生成不超过 6,000 字符、80 行且带来源 ID 的 `知识摘要.md`。它概括稳定的活跃知识；`当前状态.md` 仍只表示当前架构、关键约束和进行中事项。
7. 最后运行 `validate` 和 `maintenance-audit`，报告压缩前后的活跃记录数、活跃索引字符数、历史记录数、跳过的冲突以及待复核项。

## 约束

- 不删除原子记录，不覆盖来源，不把未经验证的会话候选提升为正式记忆。
- 不跨项目、记录类型或无关模块合并；不要为了达到阈值牺牲独立且仍有效的事实。
- `proposed` 记录不得汇总成 `accepted` 或 `active`；冲突记录先按来源优先级核实。
- 普通回忆只读取 `索引.md`；仅当用户追溯旧决定或变更原因时读取 `历史索引.md`。
- 定时任务必须先审计，只有超过维护信号或出现重复候选时才执行语义写入；无变化时应快速结束。
- 已处理或忽略的收件箱只允许移动到可恢复的归档目录，不直接删除。
