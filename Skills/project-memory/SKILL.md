# 项目长期记忆

将 Obsidian 知识库视为可审计的项目事实库，而不是聊天记录仓库。普通任务若不依赖历史信息且未产生持久事实，不要加载或写入记忆。

## 启用检查

从当前宿主已加载的项目级指令文件的 `知识体系` 章节读取：Codex 使用 `AGENTS.md`，Claude Code 使用 `CLAUDE.md`。

- `启用` 必须为 `是`。
- `项目名称` 必须存在。
- Vault 根目录优先使用当前宿主的环境变量：Codex 使用 `CODEX_MEMORY_VAULT`，Claude Code 使用 `CLAUDE_MEMORY_VAULT`；其次使用 `Vault根目录` 配置。

缺少任一必要值时停止记忆操作。不要猜测路径，不要创建替代目录。

## 选择工作模式

- **回忆**：任务明确涉及既有决策、模块关系、历史 Bug、API 使用方式、代码约定或环境配置。
- **记录**：当前工作产生了用户已确认或由代码、测试、提交证明的重要信息。
- **初始化**：知识体系已启用，且用户要求初始化、项目知识库尚不存在，或现有知识库只有结构而没有项目事实。
- **审核收件箱**：Hook 留下待处理会话，且当前任务需要恢复相关历史或用户明确要求整理记忆。

## 回忆

1. 从任务涉及的模块、源码路径、接口及已加载约定确定检索范围。按 [召回与复核](references/retrieval.md) 先查相关模块；全局约定由项目指令文件始终生效，不依赖召回命中。
2. 用 `memory_store.py maintenance-audit --module <模块>` 检查模块摘要；未指定模块时检查项目摘要。仅当 `summary.usable` 为真时读取返回的 `summary.path`，否则用 `search` 定向检索；短活跃索引只是导航，不代表全部知识。
3. 首轮默认取 3 条相关结果。跨模块修改、结果不足、分页未覆盖关键约束、来源冲突或依赖不明时，按模块、路径、接口继续检索并读取必要原文；不能因读满 3 条就停止。相关模块、全局约束和受影响公共接口已有依据，且剩余疑问已解决或明确标注后停止。
4. 默认只召回 `active|accepted|fixed`；`proposed` 不作为权威事实，`superseded|deprecated` 仅用于历史追溯。跨分支、版本或适用范围未确认的内容不得直接用于当前实现。
5. 用当前代码、测试或用户确认复核关联事实，分别说明“当前实现”“已确认但未落地的目标”“历史决定”和“尚待验证”。摘要指纹只反映知识记录变化，不证明源码仍与记录一致。

如果项目设置 `自动加载：是`，Hook 可能已注入 `当前状态.md`。它只是导航摘要，不能替代源码或正式记录。

## 记录

写入前阅读 [记录结构](references/schema.md)，然后：

1. 为信息选择类型、稳定 ID、状态、来源、模块和验证日期。全局规则使用 `--module global`；模块名称沿用项目现有名称。正文说明记录是当前事实还是已确认目标，涉及版本差异时注明仓库、分支或版本及验证基线。
2. 搜索相同 ID 和相同主题。措辞修正、补充证据更新同 ID；结论、适用范围或关键决策实质变化时新建 ID 并使用 `supersedes` 保留旧结论。目标尚未落地时保留仍真实的当前实现记录，不因目标已确认就将当前事实标为失效。
3. 由当前任务指定的唯一写入代理串行执行 `scripts/memory_store.py upsert`；更新已有记录时传入刚读取的 `--expected-fingerprint`。同一知识库的其他任务需要先协调写入时段；指纹检查和单文件原子替换不提供跨任务事务保证。不要用 `obsidian append` 拼接章节。
4. 新记录替代旧记录时设置 `supersedes`；存储脚本会把旧记录状态改为 `superseded`，并从活跃索引移入历史索引。
5. 运行 `scripts/memory_store.py validate`，确认没有重复 ID 或指纹。

正式记录必须有可核验来源。用户明确确认可以作为来源；代码事实应尽量包含文件位置、提交 SHA 或测试命令。

在重要结论已经确认或验证的工作节点及时记录，不将 SessionEnd 作为唯一收集手段。子代理只提交候选结论、适用范围和证据，由指定写入代理复核后落盘。任务改动相关源码、公共接口、依赖版本或环境配置时，按 [召回与复核](references/retrieval.md) 检查受影响记忆；未完成复核的内容明确列出，不刷新验证日期冒充已验证。

## 初始化

命令中的脚本路径应从本 `SKILL.md` 所在目录解析，不要假设当前项目包含 `Skills/` 源码目录。

初始化必须完成结构创建和首批项目数据填充，不能以空目录、空索引或占位笔记作为完成结果。

完成边界为：项目概况、主要模块导航、运行与验证方式、核心约定均有实际内容和依据。初始化不要求穷尽所有业务细节，模块内部知识随开发按需补充；不能只为填满分类增加记录。

先创建缺失结构：

```bash
python "<project-memory Skill目录>/scripts/memory_store.py" \
  --vault-root "<Vault根目录>" \
  --project "<项目名称>" \
  init
```

`init` 命令只负责创建缺失目录和基础索引，不覆盖现有笔记；执行完该命令后继续完成以下步骤：

1. 阅读 [记录结构](references/schema.md)，根据当前项目已加载的指令、README、构建配置、关键入口及相关源码，确认项目用途、主要模块、技术栈、运行与验证方式和适用约定。按这些主题定向取证，不扫描整个 Vault。
2. 将已验证信息按“记录”流程通过 `upsert` 写入首批原子笔记；每条必须有稳定 ID、来源和验证日期。按实际证据覆盖架构、环境和约定；只有存在依据时才记录决策、Bug 或 API 经验，不为填满分类编造数据。
3. 将当前项目适用的已确认约定写入 `约定/`，包括适用的“反过度工程 / 反防御性编程”规则，并注明权威指令文件来源。全局指令保存完整强制规则，记忆侧保留适用说明和来源，避免两份正文长期独立演变。重复初始化时按“记录”流程处理已有 ID 与实质变化。
4. 使用 `set-current` 填充 `当前状态.md`，概述已核实的项目现状、关键约束，并链接首批原子笔记。已有内容应按当前事实合并，不抹除仍有效的信息。
5. 运行 `validate`，检查正式记录与索引有效，并确认当前状态有实际项目内容。报告新增或更新的记录、依据和未能核实的内容。若没有足够来源填充数据，明确报告初始化未完成及缺少的资料，不将结构创建成功当作完整初始化成功。

## 审核 Hook 收件箱

`知识库/收件箱/*.json` 只记录待审核会话元数据：

1. 仅处理与当前任务有关的候选。
2. 如果 `transcript_path` 仍存在，提取可能重要的信息并以源码、测试或用户确认复核。路径已失效时尝试依据候选关联的项目源码或提交恢复；证据不足则保留 `pending` 并报告资料缺失，不能假定内容已恢复或已处理。
3. 通过 `upsert` 写入正式记录后，使用 `mark-inbox` 标记为 `processed`。
4. 没有长期价值的候选标记为 `ignored`。

不得直接把完整聊天或 Hook 候选复制进正式知识库。

## 当前状态

仅当项目当前架构、关键约束或进行中事项确实发生变化时更新 `当前状态.md`：

```bash
python "<project-memory Skill目录>/scripts/memory_store.py" \
  --vault-root "<Vault根目录>" \
  --project "<项目名称>" \
  set-current \
  --body-file "<摘要文件>"
```

保持摘要不超过 80 行；详细历史留在原子笔记中。

中大型项目的当前状态只保留全局约束、主线现状和主要模块导航；分支临时进度留在对应任务。模块摘要由维护 Skill 按需生成，将其返回路径作为链接加入导航，不要求一份项目摘要覆盖所有模块细节。

当活跃索引或同主题记录持续增长时，使用 `$project-memory-maintenance` 做分批审计和语义合并；普通回忆不要顺带扫描、总结整个知识库。
